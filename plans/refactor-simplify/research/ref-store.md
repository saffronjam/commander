# Reference store pattern: SQLite + sqlc + golang-migrate (from saffron-hive)

This is a copyable recipe extracted from `/Users/emikar/repos/saffron-hive`. It is the
exact pattern the Satisfactory Dashboard refactor should adopt for SQLite history + stateful data.

The reference stack: `modernc.org/sqlite` (pure-Go driver), `sqlc` v1.31.0 (query
codegen), `golang-migrate/v4` with the `iofs` source driver (numbered up/down SQL
files embedded via `embed.FS`), and a hand-written `*store.DB` wrapper over the
generated `*sqlite.Queries`.

---

## 1. Directory layout

```
internal/store/
  migrations/                 # numbered up/down SQL, embedded
    001_initial_schema.up.sql
    001_initial_schema.down.sql
    023_device_state_history.up.sql      # the time-series HISTORY pattern
    023_device_state_history.down.sql
    ...                                   # 98 files = 49 migration pairs
  queries/                    # hand-written sqlc query files, one per domain
    device_state_history.sql
    settings.sql
    devices.sql
    ...
  sqlite/                     # sqlc-GENERATED output (committed, never hand-edited)
    db.go                     # DBTX iface, New(), Queries, WithTx()
    models.go                 # one struct per table
    querier.go                # Querier interface (emit_interface: true)
    device_state_history.sql.go
    settings.sql.go
    ...
  migrations.go               # //go:embed migrations/*.sql  ->  var Migrations embed.FS
  store.go                    # domain-facing param/result structs (NOT generated)
  db.go                       # *DB wrapper: q *sqlite.Queries + db *sql.DB; execTx
  mapper.go                   # helpers: JSON (un)marshal, nullable ptr<->NullInt64
  retention.go                # generic retention loop (settings-driven pruning)
  history.go                  # domain methods: InsertStateSample / QueryStateHistory / Prune
  <domain>.go                 # one file per domain wrapping the generated queries
  migration_test.go           # up / up+down / idempotency tests against :memory:

sqlc.yaml                     # at repo root
cmd/migrate/migrate.go        # `app migrate up|down|version [steps]` subcommand
cmd/serve/serve.go            # opens *sql.DB with pragmas; does NOT auto-migrate
```

Key separation of concerns:
- `internal/store/sqlite/` is 100% generated by sqlc and committed to git. A `sqlc-check`
  CI target regenerates into a tmpdir and diffs to catch drift.
- `internal/store/*.go` (db.go, history.go, retention.go, the per-domain files) are
  hand-written wrappers. They expose **domain types** (`store.StateSample`,
  `store.StateHistoryQuery`) and accept/return those, converting to/from the generated
  `sqlite.*Params` / `sqlite.*Row` types internally. Callers never see the generated package.
- Consumers depend on **narrow interfaces they declare locally** (e.g. `historyStore`
  in `internal/history/recorder.go` lists only the 3 methods it uses); `*store.DB`
  satisfies them structurally. No fat repository interface.

## 2. sqlc.yaml shape

Full file from `/Users/emikar/repos/saffron-hive/sqlc.yaml`:

```yaml
version: "2"
sql:
  - engine: "sqlite"
    schema: "internal/store/migrations"      # sqlc reads the migrations as the schema
    queries: "internal/store/queries"
    gen:
      go:
        package: "sqlite"
        out: "internal/store/sqlite"
        emit_interface: true                  # generates Querier interface
        emit_pointers_for_null_types: true    # nullable cols -> *T instead of sql.NullX
        overrides:
          - column: "devices.id"
            go_type: "github.com/saffronjam/saffron-hive/internal/device.DeviceID"
          - column: "devices.source"
            go_type: "github.com/saffronjam/saffron-hive/internal/device.Source"
          # ...one entry per typed-string column
          - column: "device_state_samples.device_id"
            go_type: "github.com/saffronjam/saffron-hive/internal/device.DeviceID"
```

Notes that matter for the port:
- `schema:` points at the **migrations directory itself** — sqlc parses the up files to
  learn the schema. No separate `schema.sql`. (Down files are ignored by sqlc since they
  only DROP/recreate; sqlc applies migrations in order and tracks the resulting schema.)
- `emit_interface: true` emits a `Querier` interface (`querier.go`) so the wrapper /
  tests can mock the query layer if needed.
- `emit_pointers_for_null_types: true` makes nullable columns map to `*string`, `*int64`,
  `*time.Time` rather than `sql.NullString` etc. This is why `store.go` structs use bare
  pointers (`Icon *string`, `LastFiredAt *time.Time`) and `mapper.go` has the
  `boolToNullInt64` / `intPtrToNullInt64` helpers — to bridge Go `*bool`/`*int` to the
  generated `*int64` for nullable boolean/integer columns.
- `overrides[].column` maps a specific `table.column` to a strongly-typed Go type (a named
  string type from a domain package). This is how `device_id TEXT` becomes
  `device.DeviceID` in every generated param/row struct without manual conversion. For
  Satisfactory this is where session IDs, save names, circuit IDs, etc. get their typed
  Go aliases.

## 3. Migration file naming & conventions

- Files: `NNN_snake_case_name.up.sql` and `NNN_snake_case_name.down.sql`. `NNN` is a
  zero-padded sequential version (`001`, `002`, ... `049`). golang-migrate's `iofs`
  source parses `version_name.direction.sql`.
- Every up file has a matching down file. The down must fully reverse the up — the repo
  has `TestMigrateUpDown` that runs `Up()` then `Down()` against `:memory:` to enforce it.
- Migrations are **additive history**: never edit a committed migration; add a new one.
  (Matches the project rule "no backward compat" only in the sense of code paths — the
  migration ledger itself is append-only.)
- Migrations can carry **data seeding**, not just DDL. Example, `023_..up.sql` seeds a
  default retention setting:
  `INSERT OR IGNORE INTO settings (key, value) VALUES ('history.retention_days', '365');`
- Down files restore the prior shape (the 023 down recreates the old `sensor_history`
  table it replaced) — illustrative of "clean break" replacement migrations.

## 4. Embed + run-at-startup code

### 4a. The embed (`internal/store/migrations.go`)

```go
package store

import "embed"

// Migrations contains the embedded migration SQL files.
//
//go:embed migrations/*.sql
var Migrations embed.FS
```

### 4b. The migration runner (`cmd/migrate/migrate.go`)

Migrations are NOT applied automatically inside the serve path. They run as an explicit
`app migrate up` subcommand (see §6 for sequencing implications). Core of `Run`:

```go
func Run(_ context.Context, direction string, steps int) error {
    dbPath := os.Getenv("HIVE_DB_PATH")
    if dbPath == "" {
        dbPath = "saffron-hive.db"
    }

    db, err := sql.Open("sqlite", dbPath+"?_pragma=journal_mode(WAL)&_pragma=busy_timeout(5000)")
    if err != nil {
        return fmt.Errorf("open database: %w", err)
    }
    defer func() { _ = db.Close() }()

    sourceDriver, err := iofs.New(store.Migrations, "migrations")   // embed.FS + subdir
    if err != nil {
        return fmt.Errorf("create migration source: %w", err)
    }
    dbDriver, err := sqlite.WithInstance(db, &sqlite.Config{})      // reuses the open *sql.DB
    if err != nil {
        return fmt.Errorf("create migration db driver: %w", err)
    }
    m, err := migrate.NewWithInstance("iofs", sourceDriver, "sqlite", dbDriver)
    if err != nil {
        return fmt.Errorf("create migrator: %w", err)
    }

    switch direction {
    case "up":
        if steps > 0 {
            err = m.Steps(steps)
        } else {
            err = m.Up()        // applies all pending
        }
        if err != nil && err != migrate.ErrNoChange {
            return err
        }
    case "down":
        n := 1
        if steps > 0 { n = steps }
        if err := m.Steps(-n); err != nil && err != migrate.ErrNoChange { return err }
    case "version":
        version, dirty, err := m.Version()
        // ...
    }
    return nil
}
```

Imports:
```go
import (
    "github.com/golang-migrate/migrate/v4"
    "github.com/golang-migrate/migrate/v4/database/sqlite"   // golang-migrate's sqlite driver
    "github.com/golang-migrate/migrate/v4/source/iofs"
    _ "modernc.org/sqlite"                                    // registers the "sqlite" sql driver
)
```

`migrate.ErrNoChange` is treated as success (idempotent re-run). `migrate.NewWithInstance`
reuses the already-open `*sql.DB` rather than a connection string, so the runner and app
share identical pragmas.

### 4c. Test wiring (`internal/store/migration_test.go`)

The same `iofs.New(Migrations, "migrations")` + `sqlite.WithInstance(db, &sqlite.Config{})`
+ `migrate.NewWithInstance("iofs", ...)` chain is used in tests against
`sql.Open("sqlite", ":memory:")`. Three tests: `TestMigrateUp`, `TestMigrateUpDown`,
`TestMigrateUpIdempotent`. Adopt these verbatim — they are the safety net for the
append-only migration ledger.

## 5. The *DB wrapper and execTx (`internal/store/db.go`)

```go
type DB struct {
    q  *sqlite.Queries
    db *sql.DB
}

func New(db *sql.DB) *DB {
    return &DB{q: sqlite.New(db), db: db}
}

// execTx runs fn inside a BEGIN IMMEDIATE transaction.
func (s *DB) execTx(ctx context.Context, fn func(*sqlite.Queries) error) error {
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil {
        return fmt.Errorf("begin tx: %w", err)
    }
    if err := fn(s.q.WithTx(tx)); err != nil {
        _ = tx.Rollback()
        return err
    }
    return tx.Commit()
}
```

`s.q.WithTx(tx)` rebinds the generated queries to the transaction so multi-statement
operations stay atomic. Single-statement domain methods just call `s.q.<Method>` directly.

## 6. DB file location, WAL mode & pragmas

Two distinct `sql.Open` connection strings, both pure-Go modernc:

Migrate path (`cmd/migrate/migrate.go`):
```
dbPath + "?_pragma=journal_mode(WAL)&_pragma=busy_timeout(5000)"
```

Serve path (`cmd/serve/serve.go`):
```
cfg.DBPath + "?_pragma=journal_mode(WAL)&_pragma=busy_timeout(5000)&_txlock=immediate"
```

- `_pragma=journal_mode(WAL)` — WAL for concurrent readers + single writer.
- `_pragma=busy_timeout(5000)` — 5s wait on lock contention.
- `_txlock=immediate` — (serve only) makes `BeginTx` issue `BEGIN IMMEDIATE` instead of
  the default `BEGIN DEFERRED`. The serve.go comment is load-bearing: deferred tx take a
  read lock and upgrade to write on first write, but SQLite returns `SQLITE_BUSY`
  immediately on upgrade contention and `busy_timeout` does NOT cover that case. Taking
  the write lock upfront lets `busy_timeout` cover the full wait. Adopt
  `_txlock=immediate` for the Satisfactory serve path since the poller writes history
  concurrently with GraphQL reads.
- DB path comes from env/config (`HIVE_DB_PATH` default `saffron-hive.db`); in the real
  app it lives under a configured `cfg.DataDir`. For Satisfactory, put it under a single
  mounted volume in the consolidated container.

modernc note: the reference Dockerfile actually builds with `CGO_ENABLED=1` (golang +
`gcc musl-dev`), but that is incidental — `modernc.org/sqlite` is pure Go, so the
Satisfactory build should set **`CGO_ENABLED=0`** as the refactor goal requires. modernc
needs no cgo; just import `_ "modernc.org/sqlite"` and use driver name `"sqlite"`.

## 7. Query annotation conventions (`queries/*.sql`)

sqlc query directives seen in the repo:
- `-- name: X :one`    — single row (`RETURNING id` for inserts; returns the scalar/row).
- `-- name: X :many`   — slice of rows.
- `-- name: X :exec`   — no rows returned (e.g. UpsertSetting).
- `-- name: X :execrows`— returns `int64` rows-affected (used by all prune/delete queries).

Parameter styles:
- Named args via `sqlc.arg('name')` (preferred for readability); generates a Params struct
  field named from the arg.
- Positional `?` also used in simpler files (`settings.sql` uses `WHERE key = ?`).
- `CAST(sqlc.arg('x') AS TEXT/INTEGER)` is used to pin the Go param type when the column
  type alone is ambiguous (e.g. forcing a time param to be passed as a TEXT string).

Upsert idiom (`settings.sql`):
```sql
-- name: UpsertSetting :exec
INSERT INTO settings (key, value) VALUES (?, ?)
ON CONFLICT(key) DO UPDATE SET value = excluded.value;
```

Doc comments: a `--` comment line directly under the `-- name:` line is propagated by
sqlc into the generated Go function's doc comment (see `QueryStateHistoryBucketed`).

## 8. The time-series HISTORY pattern (migration 023 + device_state_history.sql)

This is the canonical pattern to copy for Satisfactory history (prod stats, power, etc.).

### Table + indexes (`023_device_state_history.up.sql`)

```sql
CREATE TABLE device_state_samples (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id TEXT NOT NULL REFERENCES devices(id),
    field TEXT NOT NULL,
    value REAL NOT NULL,
    recorded_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_device_state_samples_device_field_time
    ON device_state_samples(device_id, field, recorded_at);

CREATE INDEX idx_device_state_samples_recorded_at
    ON device_state_samples(recorded_at);

INSERT OR IGNORE INTO settings (key, value) VALUES ('history.retention_days', '365');
```

Design points:
- **Long-and-narrow / EAV-ish shape**: one row per `(entity, field, timestamp, value)`
  rather than a wide column-per-metric table. `field TEXT` + `value REAL` lets you record
  arbitrary scalar series without schema churn. For Satisfactory, `device_id` -> a
  session/save + producer key, `field` -> the metric name, `value` -> the number.
- **Composite index** `(device_id, field, recorded_at)` serves the primary query
  (filter by id+field, range on time, ordered). **Second index** on `recorded_at` alone
  serves the retention prune (`DELETE ... WHERE recorded_at < cutoff`).
- `id INTEGER PRIMARY KEY AUTOINCREMENT` is the rowid; queries don't use it for ordering —
  they order by `recorded_at`.

### Timestamp storage strategy (`history.go` + the queries)

The column is declared `TIMESTAMP` but values are written as **RFC3339Nano UTC strings**:
```go
func formatSampleTime(t time.Time) string { return t.UTC().Format(time.RFC3339Nano) }
```
Rationale (from the query doc comments): storing a fixed-width, UTC, RFC3339Nano text
form makes **lexicographic string comparison == chronological order**, so range queries
(`recorded_at >= from AND recorded_at <= to`) work correctly with text bounds. Mixing
formats or a local-tz label would break range comparisons.

### Three query shapes (`queries/device_state_history.sql`)

1. Insert one sample (`:one`, `RETURNING id`).
2. **Raw range query** (`:many`) — filter by JSON arrays of ids/fields, time range,
   optional limit:
   ```sql
   WHERE device_id IN (SELECT value FROM json_each(CAST(:device_ids_json AS TEXT)))
     AND (json_array_length(CAST(:fields_json AS TEXT)) = 0
          OR field IN (SELECT value FROM json_each(CAST(:fields_json AS TEXT))))
     AND recorded_at >= CAST(:from_time AS TEXT)
     AND recorded_at <= CAST(:to_time AS TEXT)
   ORDER BY device_id, field, recorded_at
   LIMIT IIF(CAST(:lim AS INTEGER) > 0, CAST(:lim AS INTEGER), -1);
   ```
   - **JSON-array params** (`json_each` over a `'[...]'` string) is sqlc's idiom for
     variable-length `IN (...)` lists, which sqlite/sqlc can't bind natively. The Go
     wrapper marshals `[]string` to JSON (`marshalStringArray`).
   - Empty `fields_json` array means "all fields" (the `json_array_length(...) = 0` branch).
   - `LIMIT IIF(... > 0, ..., -1)` — `-1` is SQLite's "no limit", so `lim<=0` means unlimited.
3. **Bucketed/downsampled query** (`:many`) — server-side averaging into fixed time
   buckets (for charting long ranges):
   ```sql
   CAST(strftime('%s', substr(recorded_at,1,19)) AS INTEGER) / CAST(:bucket_seconds AS INTEGER) AS bucket_key,
   CAST(AVG(value) AS REAL) AS bucket_value,
   CAST(strftime('%s', substr(MIN(recorded_at),1,19)) AS INTEGER) AS bucket_start_unix
   ... GROUP BY device_id, field, bucket_key
   ```
   - Returns the bucket value as `AVG` and the bucket time as an **integer Unix epoch**
     (`bucket_start_unix`). The doc comment explains why: returning an INTEGER epoch
     sidesteps the modernc driver re-serialising a `TIMESTAMP` aggregate, and
     `substr(...,1,19)` trims the RFC3339Nano fraction so `strftime('%s', ...)` parses.
   - The Go side reconstructs `time.Unix(r.BucketStartUnix, 0).UTC()`.
4. **Prune** (`:execrows`):
   ```sql
   -- name: PruneDeviceStateSamplesOlderThan :execrows
   DELETE FROM device_state_samples WHERE recorded_at < CAST(:cutoff AS TEXT);
   ```

### Generated output shape (`sqlite/device_state_history.sql.go`)

sqlc emits, per query: a `const <name> = ` SQL string (named args rewritten to `?1, ?2`),
a `<Name>Params` struct, a `<Name>Row` struct (for `:many`), and a method on `*Queries`.
The column-override types flow through automatically (`DeviceID device.DeviceID`).

### Retention / pruning loop (`internal/store/retention.go` + `internal/history/retention.go`)

Generic, settings-driven, hot-reloadable pruner:
- `store.RetentionConfig{ SettingKey, DefaultDays, Label, StartupDelay, Interval }`.
- `store.RunRetention(ctx, logger, pruner, cfg)` — waits `StartupDelay` (default 30s, lets
  hydration finish), prunes once, then re-prunes every `Interval` (default 6h). On every
  tick it **re-reads the retention window from the settings table**, so the user can
  change retention without a restart.
- `RetentionPruner` is a 2-method interface (`GetSetting`, `Prune`); the history package
  provides a thin `historyPruner` adapter binding it to
  `PruneDeviceStateSamplesOlderThan`. The default key/days
  (`history.retention_days` / `365`) match the migration seed.

### How history rows get written (the bus -> store bridge)

`internal/history/recorder.go`: `RunRecorder(ctx, bus, store)` subscribes to a single
event type on the in-process eventbus, and for each event writes one `InsertStateSample`
per non-nil scalar field. This is the exact "poller -> channel/bus -> SQLite history
recorder goroutine" wiring the Satisfactory refactor wants (plans 05 + 06). The recorder
depends only on a 3-method `historyStore` interface, not on `*store.DB` directly.

## 10. Mapping to the Satisfactory refactor

- **Replaces Redis as the store** (refactor goal 3 / plan 03): all stateful + historical
  data moves into this SQLite store. Live data does NOT go here — it flows through the
  in-process eventbus (plan 05); only history samples and config/session/auth land in SQLite.
- **History tables**: model Satisfactory time-series (prodStats, generatorStats,
  factoryStats, sinkStats, power/circuit values) on the `device_state_samples` pattern —
  long-narrow `(scope, field, value REAL, recorded_at TEXT-RFC3339Nano)` with the dual
  index (composite for range reads, single `recorded_at` for prune) and the raw +
  bucketed query pair feeding GraphQL history queries (plan 06/08). Per-save isolation
  (the existing "save name in cache keys" concern, commit 0a12da8) becomes a column
  (e.g. `save_name TEXT` / `session_id`) participating in the composite index instead of
  Redis key prefixing.
- **Config / session / settings / auth** (refactor MEANING bullets): one table each, with
  the `settings` key/value + `UpsertSetting` ON CONFLICT idiom for loose settings, and
  dedicated typed tables for sessions/users (cf. saffron-hive `users`, `settings`,
  `mqtt_config` singletons).
- **Type generation replacement** (plan 08): tygo (Go struct -> TS) for the DB layer is
  superseded by sqlc (SQL -> Go) + GraphQL codegen (schema -> TS). sqlc column overrides
  carry the project's typed string IDs into generated Go.
- **CGO**: use `CGO_ENABLED=0` with `modernc.org/sqlite` (pure Go) — keeps the consolidated
  single-image build (plan 01) static, unlike the reference Dockerfile's incidental CGO=1.

### Open decision: when to run migrations

saffron-hive runs migrations as a **separate `migrate up` subcommand**, NOT inside serve
(serve just opens the already-migrated DB). In a single-container deployment (plan 01)
this means either (a) a container entrypoint that runs `app migrate up && app serve`, or
(b) calling the migrate runner at the top of serve before `store.New`. The reference
chose (a)-style separation. The Satisfactory refactor must pick one explicitly (see open
questions) — option (b) is simpler for a single self-contained binary and is fully
compatible with this code (just call the iofs+NewWithInstance chain before opening the
serve-path `*sql.DB`, or reuse the same handle).
