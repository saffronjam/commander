# 07 — GraphQL-Native React Frontend

## Context

The `dashboard/` app today has **no GraphQL client and no HTTP client library at all**. Every
network call is hand-rolled: five REST fetchers in `src/services/` (`authApi`, `sessionApi`,
`settingsApi`, `historyApi`, `nodesApi`), a single SSE pipe in `contexts/api/ApiProvider.tsx`
that opens an `EventSource` against `/v1/sessions/:id/events`, seeds itself with one REST
snapshot of `/v1/sessions/:id/state`, dispatches ~30 `SatisfactoryEvent*` payloads into a
mutable ref, and snapshots that ref into React state on a 2-second `setInterval`. A
`SessionAwareApiProvider` force-remounts the whole live layer when `session.id` or the save
name changes. Auth is **HTTP-only cookie** (`credentials: 'include'`), and every service
converts an HTTP 401 into a `window` `auth:expired` CustomEvent that `AuthContext` listens
for. Frontend domain types come from `src/apiTypes.ts`, generated by `tygo` from Go structs.

The target mirrors saffron-hive's web data layer (urql + `@graphql-codegen/client-preset` +
`graphql-ws`), translated from SvelteKit to React 18. The single `/graphql` endpoint serves
HTTP (queries/mutations) and a WS upgrade (subscriptions). Because plan 01 collapses everything
into one Go binary that also serves the built SPA, the frontend is **same-origin**: there is no
cross-origin CORS, no separate asset host, and the `config.apiUrl` indirection
(`window.__RUNTIME_CONFIG__` / `VITE_API_URL`) collapses to relative `/graphql`. This
single-origin fact is what lets us keep cookie auth (the WS handshake carries the cookie
automatically) instead of adopting saffron-hive's Bearer-token + `connectionParams` model.

This document owns: the package deps, the codegen config, the urql `Client` + exchanges +
`graphql-ws` bridge, the deletion of the entire REST/SSE plumbing, the rebuild of the auth and
session contexts on GraphQL, and a per-route smart-query/subscription table with the hooks that
replace the old ones. **The GraphQL type/field catalog is owned by 08; every operation this
plan authors selects fields that exist in 08's catalog** — the per-domain `<domain>Changed`
subscriptions, the per-type `<domain>History` queries, and the typed snapshot queries. This
plan does **not** invent schema field names; the page-prefixed *operation* names below
(`PowerView`, `MapInfraQuery`, …) are client-side document labels, not server fields. The
backend schema, resolvers, and the eventbus bridge are owned by 05/06; this plan consumes the
SDL that gqlgen emits.

## Settled design decisions

1. **Auth stays cookie-based, not Bearer (decision E-3).** The current backend is cookie-only
   (`sd_access_token`, sliding TTL, per-IP rate limit). Once deployment is single-origin
   (plan 01), the cookie rides every `fetch` (`credentials: 'include'`) and the `graphql-ws`
   handshake (browsers send same-origin cookies on the WS upgrade automatically). The
   `graphql-ws` client sends **NO `connectionParams`** — there is no `connectionParams.authToken`
   path. 06's `wsInitFunc` reads the auth cookie off the upgrade `http.Request`. We do **not**
   port saffron-hive's `Authorization: Bearer`, `X-Refreshed-Token`, `connectionParams: { authToken }`,
   or `jwt-decode` expiry gate. The auth-expiry signal moves from the per-service `auth:expired`
   CustomEvent into a single urql `mapExchange.onError` that detects `extensions.code === "UNAUTHENTICATED"`
   or HTTP 401 and drives the existing `AuthContext` state machine.

2. **One urql `Client`, created once, provided at the root.** Replaces both
   `SessionAwareApiProvider` and `ApiProvider`. Mirrors saffron-hive's "only the layout creates
   the client" rule. Imperative access via `useClient()`; declarative via `useQuery` /
   `useMutation` / `useSubscription`.

3. **Include `cacheExchange` (urql document cache).** saffron-hive omits it (refetch-heavy);
   our dashboard has many snapshot queries (sessions list, settings, infra geometry, history
   points) that benefit from document caching, and mutations declare their invalidations
   naturally. We use the **document** cache, not Graphcache — no normalized cache, no
   hand-written `updates`/`keys` config to maintain. Live data does not flow through the cache;
   it flows through subscriptions into React state.

4. **`graphql()` typed documents, authored inline, colocated per view.** No standalone
   `.graphql` files. Every operation has a globally-unique, page-prefixed name
   (`PowerView`, `MapInfraQuery`, `MapVehiclesSub`, `OverviewHistory`) because client-preset
   keys its `Documents` map by operation name across the whole project. **The page prefix is the
   only naming freedom this plan has; the selection set inside each document uses 08's exact
   field names** (e.g. the `PowerView` subscription document selects the `circuitsChanged` field).

5. **`DateTime` scalar maps to `string`.** History charts lean on `gameTimeId` (`Int!`) ordering;
   the only `DateTime` field on the wire is `Session.createdAt` (08). We map custom scalars to
   `string` in codegen `config.scalars` rather than inheriting `any`. There is **no `Int64`
   scalar** (decision E-2): `gameTimeId` and `shipReturnTime` are plain `Int`, which codegen maps
   to `number`.

6. **Live data = "snapshot query once, then merge subscription deltas".** A single app-lifetime
   `LiveStateProvider` does the initial typed snapshot queries and runs the per-domain
   `<domain>Changed` subscriptions, merging deltas into one context value exposed via
   `use-context-selector` (which the codebase already depends on). This preserves the existing
   selective-subscription read pattern (`useContextSelector(ApiContext, v => v.circuits)`) while
   removing the SSE ref + 2s tick. Pages that need a *narrow* live slice may instead issue a
   page-scoped `useSubscription` directly (e.g. `/power` needs only `circuitsChanged`).

7. **Session switching is done via subscription/query variables, not remount.** Changing
   `selectedSessionId` changes the `sessionId` variable on the live queries + subscriptions; urql
   tears down the old WS operations and starts new ones, and the document cache keys results by
   variables. The `SessionAwareApiProvider` remount hack is deleted.

8. **Loading convention: explicit `fetching` + shadcn `Skeleton`, project-wide.** Not Suspense.
   This matches the existing component structure (views already branch on `isLoading`) and the
   incremental nature of live data. The root `<Suspense>` boundary in `main.tsx` stays only for
   lazy route code-splitting, not data.

9. **Client-local view prefs stay in `localStorage`.** `hooks/use-settings.ts`
   (`productionView`, `historyDataRange`, `historyWindowSize`) is a view concern, not server
   state, and stays local (08 confirms: these are client-only UI preferences, not the server
   `Settings` row). They drive the `since`/`maxPoints` arguments of the `<domain>History` queries.
   Only the server-global `Settings` (`logLevel`) becomes a query/mutation.

## urql Client + exchanges + graphql-ws bridge

File: `dashboard/src/gql/client.ts` (ADD)

```ts
import { Client, cacheExchange, fetchExchange, mapExchange, subscriptionExchange } from "urql";
import { createClient as createWSClient } from "graphql-ws";

const GRAPHQL_HTTP = "/graphql";

function wsUrl(path: string): string {
  const url = new URL(path, window.location.origin);
  url.protocol = url.protocol === "https:" ? "wss:" : "ws:";
  return url.toString();
}

export type AuthExpiredHandler = () => void;

export function createGraphQLClient(onAuthExpired: AuthExpiredHandler): Client {
  const wsClient = createWSClient({
    url: wsUrl(GRAPHQL_HTTP),
    lazy: true,
    shouldRetry: () => true,
  });

  return new Client({
    url: GRAPHQL_HTTP,
    fetchOptions: { credentials: "include" },
    exchanges: [
      mapExchange({
        onError(error) {
          const unauth =
            error.response?.status === 401 ||
            error.graphQLErrors.some((e) => e.extensions?.code === "UNAUTHENTICATED");
          if (unauth) onAuthExpired();
        },
      }),
      cacheExchange,
      fetchExchange,
      subscriptionExchange({
        forwardSubscription(request) {
          const input = { ...request, query: request.query || "" };
          return {
            subscribe(sink) {
              return { unsubscribe: wsClient.subscribe(input, sink) };
            },
          };
        },
      }),
    ],
  });
}
```

Notes carried from the reference, adapted to cookie auth (decision E-3):

- **No custom `fetch` wrapper, no Bearer header, NO `connectionParams` (decision E-3).** Cookie
  auth means `fetchOptions: { credentials: "include" }` on HTTP and the same-origin cookie on the
  WS upgrade — the browser attaches it automatically; the client passes `connectionParams`
  nothing. 06's `wsInitFunc` reads the cookie off the upgrade `http.Request`. The reference's
  `authenticatedFetch` / `X-Refreshed-Token` rotation and `connectionParams: { authToken }`
  callback are dropped; the server refreshes the cookie TTL via `Set-Cookie` on the GraphQL POST
  response, which the browser applies transparently.
- **Exchange order**: `mapExchange` (401/UNAUTHENTICATED side-effect) → `cacheExchange`
  (document cache) → `fetchExchange` (HTTP) → `subscriptionExchange` (routes subscription ops
  to the WS client). `forwardSubscription` body is byte-for-byte the framework-agnostic urql
  core form from saffron-hive (`research/ref-web.md` §2).
- **Reconnection (decision E-9)**: `graphql-ws` reconnects automatically (`shouldRetry: true`,
  `lazy: true`); urql re-subscribes active subscription operations on reconnect. Because the
  cookie is sent fresh on each WS handshake, a reconnect re-authenticates with the current cookie
  with no extra code. On reconnect the `LiveStateProvider` (1) re-snapshots live state via the
  typed snapshot queries (`requestPolicy: "network-only"`) and (2) re-runs each `<domain>History`
  query with `since = <latest gameTimeId>` to close any gap during the disconnect window. There
  is **no `historyAppended` subscription** (decision E-9) — live history points arrive on the
  five `<domain>Changed` subscriptions and charts stitch them by `gameTimeId`.

### Auth (`contexts/auth/AuthContext.tsx` — CHANGE, keep the state machine)

Keep the `AuthProvider` state shape (`isAuthenticated`, `usedDefaultPassword`,
`sessionExpired`). Replace the data ops with operations selecting 08's exact auth fields
(`AuthStatus { authenticated usedDefaultPassword }`, `LoginResult { success usedDefaultPassword }`,
`LogoutResult { success }`, `ChangePasswordResult { success message }`):

- `checkAuthStatus()` → `useQuery({ query: AuthStatusDocument })`
  (`query AuthStatus { authStatus { authenticated usedDefaultPassword } }`), run once on mount;
  map result into state. `authStatus` is the only public query (08).
- `login(password)` → `useMutation(LoginDocument)`
  (`mutation Login($input: LoginInput!) { login(input: $input) { success usedDefaultPassword } }`).
- `logout()` → `useMutation(LogoutDocument)`.
- `changePassword(...)` → `useMutation(ChangePasswordDocument)`
  (`mutation ChangePassword($input: ChangePasswordInput!) { changePassword(input: $input) { success message } }`).
- Expiry: expose `markSessionExpired()` (sets `sessionExpired`, clears auth). This is the action
  `GraphQLClientProvider` passes to the client's `onAuthExpired`, replacing the
  `window` `auth:expired` CustomEvent + per-service `dispatchAuthExpired` choke point. The
  `window` event listener is removed.

> **Release/upgrade note surfaced in the UI (decision D-A).** Auth cutover is a CLEAN WIPE: on
> first SQLite boot the DB is empty and auth re-bootstraps to `SD_BOOTSTRAP_PASSWORD` with
> `usedDefaultPassword = true`. After upgrade every client must log in again and the operator must
> re-set the password. The login view already keys "must change default password" off
> `usedDefaultPassword`; no client change is needed beyond confirming that prompt still fires.

Because `AuthProvider` must wrap `GraphQLClientProvider` (the client needs `markSessionExpired`),
but the auth *queries* need the urql client — split it: `AuthProvider` owns only the state +
`markSessionExpired`; a small inner `AuthDataLoader` (mounted under `GraphQLClientProvider`) runs
the `authStatus` query and the login/logout/changePassword mutations, pushing results up via the
auth context's setters. This avoids a provider ordering cycle.

Keep `selectedSessionId` selection + `localStorage` persistence
(`satisfactory-dashboard-selected-session`). Replace, selecting 08's `Session` fields
(`id name address sessionName isOnline isPaused isDisconnected stage createdAt`):

- `refreshSessions()` / 20s status poll → `useQuery({ query: SessionsDocument })`
  (`query Sessions { sessions { id name address sessionName isOnline isPaused isDisconnected stage } }`)
  plus a `useSubscription({ query: SessionUpdatedDocument }, reducer)` selecting
  `sessionUpdated(sessionId: $sessionId) { ... }` (08's per-session live `Session` payload — the
  old `sessionUpdate` SSE control event). The `setInterval` poll is deleted; live status arrives
  over the subscription.
- CRUD → mutations consumed via `useMutation`: `createSession(input)`, `updateSession(id, input)`,
  `deleteSession(id)`, `validateSession(id)`; `previewSession(address)` and `clientIp` become
  queries (08 mutation/query catalog). `validateSession` is a mutation in 08, not a query.
- `updateSessionFromEvent` is replaced by the `sessionUpdated` subscription reducer.
- **Document-cache caveat (R11):** with the document `cacheExchange`,
  `createSession`/`deleteSession`/`updateSession` mutations do **not** auto-update the `Sessions`
  query result. After each session mutation, call `reexecuteQuery({ requestPolicy: "network-only" })`
  on the `Sessions` query (or re-run it) so the list reflects the change. This is the standard
  document-cache invalidation pattern, applied wherever a mutation changes a cached list result.

### Live state (`contexts/live/LiveStateProvider.tsx` — ADD; the core replacement for ApiProvider)

This is the "snapshot-then-deltas" provider. It:

1. Reads `selectedSessionId` from `SessionProvider`.
2. Issues the initial **typed snapshot queries** for the slices the app seeds — each is its own
   concrete query from 08 (there is no `liveState` / `sessionState` catch-all object, decision
   D-C). The provider composes a single document selecting the snapshot queries it needs, e.g.
   `query LiveSnapshot($sessionId: ID!) { circuits(sessionId:$sessionId){...} factoryStats(sessionId:$sessionId){...} prodStats(...){...} sinkStats(...){...} generatorStats(...){...} players(...){...} satisfactoryApiStatus(...){running pingMs} schematics(...){...} }`,
   run with `pause: !sessionId`. These read the poller's in-memory `LatestStore` server-side.
3. Runs the per-domain `useSubscription` calls (each with a reducer merging into a single record
   keyed by id / replacing the slice), selecting 08's `<domain>Changed` fields:
   `circuitsChanged`, `factoryStatsChanged`, `prodStatsChanged`, `sinkStatsChanged`,
   `generatorStatsChanged`, `playersChanged`, `satisfactoryApiStatusChanged`,
   `connectivityChanged`, `schematicsChanged`, etc. Each takes `sessionId: ID!` and the resolver
   filters server-side. `isOnline`/disconnect state arrives via
   `satisfactoryApiStatusChanged` + `connectivityChanged` (08: `ConnectivityStatus { isOnline
   isDisconnected stage }`).
4. Exposes the merged value + `isLoading` (snapshot `fetching`) + `isOnline` via a
   `use-context-selector` context, so existing consumers keep the
   `useContextSelector(LiveStateContext, v => v.circuits)` read pattern with minimal churn.
5. On WS reconnect (detected by an urql operation restart / a `connectivityChanged` event),
   re-runs the snapshot query (`reexecuteQuery({ requestPolicy: "network-only" })`) AND re-runs
   each `<domain>History` query with `since = <latest gameTimeId>` (decision E-9) to resync —
   replacing the old "online-after-offline → re-fetch full state" branch.

`isOnline` previously came from the `satisfactoryApiCheck` SSE event and offline came from
`sessionUpdate`. Both become subscription fields (`satisfactoryApiStatusChanged` and
`connectivityChanged`; 05 owns the eventbus offline-event design); `LiveStateProvider` surfaces
them as `isOnline` so `ConnectionChecker` and views read them unchanged.

History pattern detail (`/`, `/production`): the old `useHistoryData` did an initial REST
`fetchHistory` then fired an incremental `fetchHistory({ since: latestId })` on every SSE tick,
plus client-side downsampling/pruning. The GraphQL form is a per-type parameterized `useQuery`
against the typed `<domain>History` query (08; no opaque `data` field, no `HistoryChunk`
envelope). Example for the circuits chart:

```tsx
const OVERVIEW_HISTORY = graphql(`
  query OverviewHistory($sessionId: ID!, $saveName: String!, $since: Int, $maxPoints: Int) {
    circuitsHistory(sessionId: $sessionId, saveName: $saveName, since: $since, maxPoints: $maxPoints) {
      gameTimeId
      circuits {
        id
        fuseTriggered
        consumption { total max }
        production { total }
        capacity { total }
        battery { percentage capacity differential untilFull untilEmpty }
      }
    }
  }
`);

const [{ data, fetching }] = useQuery({
  query: OVERVIEW_HISTORY,
  variables: { sessionId, saveName, since: 0, maxPoints },
});
```

Each history-enabled domain has its own query and its own concrete `<Type>HistoryPoint` return
(`circuitsHistory → [CircuitsHistoryPoint!]!`, `prodStatsHistory → [ProdStatsHistoryPoint!]!`,
etc.). `saveName` is **mandatory** (decision E-11): the client passes the save it is charting,
obtained from `historySaves(sessionId)` (08, returns `[String!]!`), defaulting to the session's
current save (read from live state). `maxPoints` triggers server-side keep-last bucketing
(08/E-6), replacing the old client-side `downsampleDataPoints`.

Incremental append (decision E-9): there is **no `historyAppended` subscription**. Live points
arrive on the relevant `<domain>Changed` subscription (whose payload corresponds to the latest
`gameTimeId`); the chart stitches them onto the history series by `gameTimeId`. On WS reconnect,
re-run the `<domain>History` query with `variables.since = <latest gameTimeId>` and
`requestPolicy: "network-only"` (the `LiveStateProvider` reconnect path drives this). The
`historyDataRange` / `historyWindowSize` client prefs (localStorage, `use-settings.ts`) map to
the `since` / `maxPoints` arguments.

Operation naming: every document is uniquely named with its page prefix
(`PowerView`, `MapInfraQuery`, `MapVehiclesSub`, `OverviewHistory`, `DronesLive`, …) so
client-preset's `Documents` map has no collisions across the project. These are document labels;
the selected fields are always 08's field names.

## Risks

- **WS cookie auth on the upgrade (decision E-3).** Subscriptions authenticate solely off the
  same-origin cookie on the WS upgrade (no `connectionParams`). If 06's `wsInitFunc` does not
  validate that cookie, subscriptions silently fail to authenticate. Validate the WS upgrade auth
  path early (step 3).
- **Cookie on WS reconnect after expiry.** If the cookie expires while a WS connection is open,
  the open socket keeps working until it drops; only on reconnect is the stale/absent cookie
  rejected. Confirm whether 06's server re-validates per subscription message or only at connect
  (security + UX).
- **Live-store re-render cost.** `LiveStateProvider` merging many `<domain>Changed` slices into
  one context risks broad re-renders if `use-context-selector` is not used carefully; keep
  equality guards on reducers (port the existing `statesEqual` idea) and select narrow slices.
- **Operation-name collisions.** client-preset fails the build on duplicate operation names;
  the page-prefix convention must be enforced from the first migrated view.
- **`/map` infra freshness.** If belt/pipe/rail geometry actually changes mid-save, the one-shot
  infra snapshot query goes stale; the snapshot query can be re-executed at low frequency, or the
  relevant infra `<domain>Changed` subscription added later if needed.
- **Document cache vs mutations (R11).** With `cacheExchange` (document cache, not normalized), a
  `createSession`/`deleteSession`/`updateSession` mutation will not auto-update the `Sessions`
  query result; the affected views/contexts must `reexecuteQuery({ requestPolicy: "network-only" })`
  after the mutation. This is wired into `SessionProvider` (above).
- **Unlockables gate first-paint (B12-005).** The `useUnlockables` gate must read `schematics`
  from a source seeded by the snapshot query before the first `schematicsChanged` tick; if the
  snapshot query omits `schematics`, the gate is subscription-only and may briefly mis-gate. The
  snapshot query in `LiveStateProvider` includes `schematics` for exactly this reason.

## How this satisfies the done-criteria

- **No REST, no SSE on the client**: all five `services/*Api.ts` and the `EventSource`-based
  `ApiProvider` are deleted; the only transport is the urql `Client` against `/graphql`
  (HTTP + `graphql-ws`).
- **GraphQL replaces API polling entirely — history AND live, fully typed (decision D-C)**:
  history is per-type `<domain>History` queries (`saveName` mandatory, `since` cursor, `maxPoints`
  bucketing) returning concrete `<Type>HistoryPoint` arrays read from SQLite (06/04); live state
  is typed snapshot queries plus per-domain `<domain>Changed` subscriptions bridged from the Go
  eventbus (05/06). No `liveState`, no `HistoryChunk`, no opaque `data` field crosses the wire.
  The 2s snapshot tick and 20s session poll are gone.
- **UI data fetching is GraphQL-native**: every view consumes typed `graphql()` documents via
  `useQuery`/`useMutation`/`useSubscription`; `apiTypes.ts`/tygo is replaced by
  `@graphql-codegen/client-preset` output in `src/gql/` (the codegen is step 3 of 08's
  `make generate` pipeline, decision E-8).
- **No WSS / cross-origin complexity**: single-origin (plan 01) means relative `/graphql`,
  cookie auth on both HTTP and WS (no `connectionParams`, decision E-3), no `__RUNTIME_CONFIG__`,
  no CORS, no separate asset host.
- **No distributed-polling artifacts**: `services/nodesApi.ts`, the `/debug/nodes` page, and the
  node/lease types are deleted with no GraphQL replacement.
